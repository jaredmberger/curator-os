# Durable Project Records

CuratorOS treats Project Records as the permanent internal knowledge corpus. Browser `localStorage` is only a working cache and offline fallback.

## Production architecture

The live CuratorOS UI is served from GitHub Pages at:

`https://curator.oceanliners.net/`

GitHub Pages cannot execute `/api/project-records`. The durable records API therefore runs in the CuratorOS Cloudflare Worker generated by `scripts/build.js`.

Production flow:

`CuratorOS UI (GitHub Pages)`
→ `https://curator.oceanliners.net/api/project-records`
→ `Cloudflare Worker route`
→ `CURATOROS_RECORDS` KV

The Worker stores one versioned corpus document under the KV key:

`project-records`

## Required Cloudflare configuration

### 1. Deploy the CuratorOS Worker

Build/deploy the Worker generated from `scripts/build.js` so the deployed Worker contains the current Project Records API.

### 2. Bind KV

Bind the CuratorOS records KV namespace to that Worker using the exact binding name:

`CURATOROS_RECORDS`

This is a **Worker KV binding**, not a Cloudflare Pages Functions binding.

### 3. Add the Worker route

Route only the API path to the Worker:

`curator.oceanliners.net/api/*`

Do **not** route `curator.oceanliners.net/*` to the Worker. The main application should continue to be served by GitHub Pages.

This split allows:

- `/` and normal CuratorOS assets → GitHub Pages
- `/api/project-records` → Cloudflare Worker + KV
- `/api/project-records/health` → Cloudflare Worker health check

### 4. Protect the route with Cloudflare Access

Project Records are internal institutional data and the API supports writes. The `curator.oceanliners.net` Access policy must include `/api/*` so unauthenticated visitors cannot read or replace the corpus.

Do not expose the write endpoint publicly.

## API behavior

### Health

`GET /api/project-records/health`

Healthy response:

```json
{
  "ok": true,
  "service": "curatoros-project-records",
  "storage": "kv",
  "binding": "CURATOROS_RECORDS"
}
```

### Load corpus

`GET /api/project-records`

Returns the durable records array plus version, timestamp, and the explicit `storage: "kv"` marker.

### Save corpus

`PUT /api/project-records`

Replaces the approved corpus, increments the storage version, and returns an explicit Worker/KV confirmation.

The CuratorOS browser client refuses to mark a save as permanent unless the response can be verified as coming from the durable KV backend.

## Browser-cache behavior

The browser cache remains useful for resilience and offline work, but it is not the source of truth.

CuratorOS reports one of these states:

- **Permanent store connected** — data came from KV.
- **Using local cache** — the remote API is unavailable or not yet routed.
- **Permanent save pending** — the browser contains a newer attempted save that did not reach KV.

If the API path is still falling through to GitHub Pages, CuratorOS now reports that the durable API route is not active rather than silently treating the response as permanent storage.

## First initialization

After the Worker route, KV binding, and Access protection are confirmed:

1. Open CuratorOS Project Records.
2. Confirm the interface reports **Permanent store connected**.
3. Import the current authoritative CuratorOS project export once, or create the first canonical record.
4. Reload CuratorOS in another browser/device.
5. Confirm the same records return from KV.

At that point, the institutional corpus is durable independently of any single iPad, browser profile, or local cache.
